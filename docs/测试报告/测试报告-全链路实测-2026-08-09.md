## ⚠️ 0. 方法论与限制声明（先读这一节，再看任何结论）

### 0.1 硬约束：本次没有可用的 API Key

- 模型 Key 只存在于 VS Code `SecretStorage`，Node 侧无法读取；环境变量中也不存在任何可用模型 Key。
- 因此**无法做「真模型端到端」实测**。若强行跳过，只能得到「代码没崩」这种无信息量结论。

### 0.2 采用的替代方法：白盒 record / replay

分三步，全程不改任何功能源码：

1. **Record（录制）**：向 `WritingWorkflows` 注入一个自实现的 `CompletionClient`（`ports.ts` 定义的接口），把产品真实拼装出的 system / user prompt 原样 dump 到 `/tmp/tw-qa/prompts/*.md`。
2. **QA 充当 LLM**：人工阅读 dump 出的 prompt，按 prompt 要求的 schema 产出响应，存成 `/tmp/tw-qa/fixtures/*.txt`。
3. **Replay（回放）**：把 fixture 喂回同一个注入点，重跑整条链路。于是 `parseModelJson` / `parseOptionCandidates` / `parseGeneratedStyle` / `normalizeOutlineNode` / `candidateViolations` / `metrics` **全部是产品真实代码在跑**。

### 0.3 ⚠️ 这个结论会高估什么（必须写在前面）

> **模型响应由 QA 充当 LLM 产出，会高估真实模型在窄窗口下的通过率。**

具体地：

| 维度 | 本次实测的可信度 | 说明 |
| --- | --- | --- |
| Prompt 拼装是否正确、约束是否注入 | **高（可直接采信）** | prompt 是产品真实生成的，逐字可查 |
| 解析层健壮性（parse*/normalize*） | **高（可直接采信）** | 跑的是产品真实代码 |
| 硬门槛判定（字数/对话比/aiSmell/violations） | **高（可直接采信）** | 跑的是产品真实 `metrics.ts` |
| **模型能否稳定产出合规 JSON** | **低（本次必然通过，不代表真实）** | QA 写的 fixture 天然合规 |
| **模型几轮能收敛到 1200–1500 字 + 35–50% 对话** | **偏乐观** | 真实模型没有 QA 的「知道门槛在哪」这一先验 |

为降低乐观偏差，本次刻意采用两条纪律：
- 每一轮 fixture **先按 prompt 自然写作，写完直接喂进去**，不预先用度量脚本"对答案"式微调（第1章 r1、第2章 r1/r2、第3章 r1/r2 均如此）；
- 只有在收到产品真实回吐的 violations 之后，才按 violations 做针对性修订——**这就是真实产品里用户的操作路径**。

即便如此，三章仍**各用了 3 轮**才全绿。真实模型只会更多，不会更少。

**根因链（三处共同作用）**：

1. `packages/core/src/prompts.ts:402-416` `planningPrompt`
   - 输出 schema `{"genre","targetReader","tags",...,"coreConflict",...}` **强制模型重新吐出用户已经选好的字段**；
   - 5 条硬性规则里**没有任何一条**说「用户已填/已选的字段必须原样沿用」；
   - schema 里**根本没有** `coreConflictType`，模型无从知道该与哪个冲突类型对齐。
2. `webview/src/features/PlanningFeature.tsx:156-162`
   - `typeof data.X === 'string' ? data.X : next.planning.X` —— 只要模型返回了字符串就**无条件覆盖**用户选择。
3. `webview/src/features/PlanningFeature.tsx:163-164`
   - `titleCandidates: stringArray(data.titleCandidates) ? data.titleCandidates : []`
   - `emotionalBeats: Array.isArray(data.emotionalBeats) ? data.emotionalBeats : []`
   - 与其余字段的 `: next.planning.X` 策略**不一致**，退化为 `[]` 造成**静默数据丢失**。

**用户可感知后果**：用户在环节 4 辛苦点选的读者画像 / 标签 / 冲突，点一下「AI 补强」就被无声改掉；书名候选可能直接消失；冲突类型 chip 与冲突正文对不上。

### 🔴 P0-1｜`dialogueRatio` 不识别直角引号「」，导致对话占比恒为 0%，修订循环永远无法收敛

- **文件**：`packages/core/src/metrics.ts:17-22`
- **代码**：
  ```ts
  const dialogueCharacters = [...text.matchAll(/[“"][^”"]+[”"]/g)]
    .reduce((total, match) => total + match[0].length, 0);
  return Math.round(dialogueCharacters / text.length * 100);
  ```
- **实测证据（第1章 r1/r2）**：
  | 稿件 | 人工可见对话 | `「」`字符数 | 正则命中 | `dialogueRatio` 判定 |
  | --- | --- | --- | --- | --- |
  | 第1章 r1 | 满篇对白 | 262 | 0 | **0%** → 违规 |
  | 第1章 r2（补写更多对白） | 更多对白 | 335 | 0 | **仍是 0%** → 仍违规 |
  | 第1章 r2 原文**仅把「」替换成“”**，一字未改 | 同上 | 0 | 335 | **24%** |
- **危害等级 P0 的理由**：
  1. 用户看到的提示是「对话占比 0%，本章目标 35—50%」，而他眼前的正文**满屏都是对话**——提示与事实直接矛盾；
  2. 修订指令会引导模型「再加对话」，**加得越多越不达标**，形成**永不收敛的死循环**，直到用完 6 轮上限；
  3. `「」` 是中文网文主流对白标点之一，**产品自身在 `prompts.ts` 的 `openings`/`bannedPatterns` 示例里就大量使用 `「」`**（如 `prompts.ts:40,48,56,133,239`），UI 上直接展示给用户看，进一步诱导这种写法。
- **附带缺陷（P2 级，同一函数）**：
  - 分母用 `text.length`（**含空白与换行**），而 `countCharacters` 是 `text.replace(/\s/g,'')`（**去空白**）。同一段正文两个口径差 2–3pp（实测 37% vs 39%）。对话行多、空行多的稿件被系统性低估，本就窄的 35–50% 窗口被进一步压缩。
  - 字符类 `[“"]…[”"]` 允许**错配**（如 `“` 配 `"`），且正文中出现的 ASCII 直引号（代码片段、英文引用）会被误计为对话。
- **建议**：正则扩为 `/[“"「『][^”"」』]+[”"」』]/g`（或按成对分别匹配），分母改用 `countCharacters(text)`，与字数口径统一。
- **路由：→ Engineer（寇豆码）**

## 4. 窄窗口震荡：1200–1500 字 × 35–50% 对话 的可用性风险（数据支撑）

这不是 bug，但**三章各 3 轮**的数据说明门槛设计本身有问题，建议产品侧评估。

两个门槛在数学上**互相拉扯**：
- 对话行短、空行多 → `text.length` 涨得比 `countCharacters` 快 → 补字数时对话占比被稀释；
- 补对话 → 占比逼近 50% 上限（第2章 r2 实测**顶格 50%**，再加一句就越界）；
- 补叙述 → 占比往 35% 下限掉（第3章 r3 一度精确落在 **35%** 边界）。

实测三章的震荡路径：

| 章 | r1 | r2 | r3 |

| 第1章 | 字数❌ 对话❌ | 字数✅ 对话❌（P0-1 所致） | 全绿 |
| 第2章 | 字数❌ 对话✅(46%) | 字数❌ 对话✅(**50% 顶格**) | 全绿 |
| 第3章 | 字数❌ 对话❌(24%) | 字数❌ 对话✅(37%) | 全绿 |

**注意**：QA 在第3轮是**知道门槛公式**才一次调平的；真实模型没有这个先验，且看不到 `text.length` 与 `countCharacters` 的口径差。**修好 P0-1 之后再评估真实轮次，不建议现在放宽窗口**——本轮 9 次出稿里有 2 次（第1章 r1/r2）纯粹浪费在 `「」` 正则缺陷上，占 22%。

> 🔄 **第 2 轮口径修正后的更新（2026-08-09）**：P0-1 修好后重算，本节结论**不但成立，而且比首轮描述更紧**：
